# 分别设置每一层防护

现在可以让一层只记录检查结果，同时让其他层继续拦截。例如，先观察任务偏移检查是否经常误报，危险命令、记忆投毒和外部内容检查仍按原来的方式处理。默认仍是五层开启并实际拦截。

## 工作台怎么用

打开一份工作的“防护记录”，展开“修改防护开关”。每层有启用开关和处理方式：

| 设置 | 实际行为 |
|---|---|
| 关闭启用开关 | 这一层不检查，也不拦截。 |
| 跟随默认处理方式 | 使用下方的默认方式；旧配置原来的全局模式保持这个含义。 |
| 拦截或等本人确认 | 这一层检查未通过时停止，或转入本人核对。 |
| 只记录，不拦截 | 这一层仍检查，记录原本会阻止或需确认的结果，然后放行。 |

单独选择的方式优先于默认方式。例如，默认选“只记录”，危险命令层单独选“拦截”，危险命令层仍会拦截。页面摘要显示每层**实际采用的方式**，不会把混合设置笼统描述为全部拦截或全部观察。

“恢复全部开启”会把五层和这份工作支持的扫描选项开启，清除各层单独设置，默认方式改为拦截。点击“保存防护设置”才生效。这是恢复推荐默认值，不是恢复创建时设置或撤销上次修改。

## 恢复创建时设置与修改记录

新实例会把创建时确认的防护设置保存为主机私有快照，并固定它的摘要。之后的修改和重置都不会覆盖这份快照。

点击“恢复创建时设置”会先把当时的值填入表单，并列出具体变化，例如“技能语义检查：开启 → 关闭”。核对后再点击“保存防护设置”。这与“恢复全部开启”不同：创建时若选择了观察模式，恢复也会回到那个观察模式。

带 `settings_history_v1` 的新实例，每次工作台保存都核对打开页面时的设置版本；期间有人修改设置，旧页面的保存会被拒绝，需刷新核对。手动修改恢复预览会改为普通设置修改，仍保留版本核对。恢复还会核对创建时快照的摘要和完整设置值，不能用另一份配置冒充基线。

防护记录会显示本次由工作台、命令行还是主机管理入口保存，是普通修改、恢复全部开启还是恢复创建时设置，以及每个变化字段的原值和新值。记录只包含允许修改的防护开关和模式，不包含工作目标、模型密钥或资料正文；没有变化的字段不伪造差异。

没有 `defense_baseline_v1` 的旧实例会明确显示“没有保存创建时设置”，不能把当前配置当作创建时配置。新快照仅在创建时生成，不提供替换或编辑入口。恢复也会作废未使用的审批与草稿，并继续保持暂停或永久撤权。

## 安装检查可以分别调整什么

| 选项 | 控制范围 | 关闭后仍保留什么 |
|---|---|---|
| 基础配置检查 | 入口认证、提权、直接联网、隔离、凭证位置、工具清单等配置规则，以及配置的模型检查。 | 配置输入格式校验、已开启的技能规则及语义检查、固定技能快照和实际运行隔离。 |
| 技能语义检查 | 是否把所列技能的完整内容交给检查模型；支持用途对照的新工作还会比较说明与所属文件的实际行为。 | 已开启的基础配置和技能规则检查、文件安全读取与快照完整性检查。 |
| 技能规则检查 | 已知恶意指令、角色伪装、凭证窃取与长编码内容的规则检查。 | 已开启的基础配置和技能语义检查、文件安全读取与快照完整性检查。 |

这些选项由“安装与技能检查”这一层统领；整层关闭时，它们都不执行。技能规则与语义可分别关闭。即使两者都关闭，开启的基础层仍安全读取全部文件；固定技能快照、主机权限和隔离要求由其他运行边界继续执行，关闭扫描不授予额外权限。

关闭任意扫描选项后，报告会列出没有检查的项目，并保留 `complete=false`；允许启动不代表做完全部检查。保存新设置后，旧基础报告标为旧设置，新的启动检查在下次启动时执行。

## 技能说明与代码如何对照

带 `skill_purpose_v1` 的新工作会把每个显式选中的技能目录视为一个技能，以该目录根部的 `SKILL.md` 说明其用途。每个文件都会连同这份完整说明一起检查；两者均来自同一次安全读取的固定快照，并附路径、字节数和内容摘要。子目录中的同名文件不能替换根部用途，也不会读取技能目录外的说明。正常的辅助脚本、测试、示例和安装代码不因功能不同就自动判为攻击。

说明缺失、空白、只有标题或仅有 `name` 时，会要求补充说明，记录 `skill_purpose_missing`，不称检查完整。普通 Markdown 正文和常用 front matter 的 `description` 均可提供说明；判断器收到完整原文，遇到没有可辨用途的其他形式也应返回待核对。规则只检查说明是否存在，真实用途和代码是否矛盾仍依赖检查模型，存在误报与漏判。

来源目录后来发生变化不会改变已固定的用途；固定快照本身被改动则不能通过实例验证。检查不执行技能代码，也不授权技能扩大原任务权限。当前组件证据见[技能对照验证](evidence/skill-purpose-2026-09-12/REPORT.zh-CN.md)。

## 命令行与旧实例

带 `per_layer_settings_v1` 标记的新实例支持这些新字段：

```json
{
  "mode": "enforce",
  "alignment_mode": "observe",
  "foundation_config_enabled": true,
  "skill_semantic_enabled": false
}
```

每层的 `input_mode`、`memory_mode`、`command_mode`、`alignment_mode`、`foundation_mode` 可填 `inherit`、`enforce` 或 `observe`；对应的 `*_enabled` 仍是启用开关。

独立技能规则开关另要求 `skill_rules_v1`，字段为 `skill_rules_enabled`。界面只对支持的工作显示该开关；CLI 与主机入口在写入前拒绝给旧工作增加此字段。新版创建时快照使用版本 2，包含规则开关；旧版快照版本 1 按原来的完整字段读取和恢复，不补造新字段，也不重写原快照。

独立创建、没有交给工作台管理的实例可以使用 CLI：

```bash
yuanxingmu defense get --profile /path/to/standalone-profile
yuanxingmu defense set --profile /path/to/standalone-profile --alignment-mode observe --skill-semantic off
yuanxingmu defense set --profile /path/to/standalone-profile --alignment-mode inherit
yuanxingmu defense set --profile /path/to/standalone-profile --skill-rules off
yuanxingmu defense reset --profile /path/to/standalone-profile
```

独立实例需要恢复创建时设置时，先运行 `get` 核对返回的 `baseline.settings`、`baseline.sha256` 和 `policy_sha256`，再使用这两个实际摘要：

```bash
yuanxingmu defense restore --profile /path/to/standalone-profile \
  --baseline-sha256 BASELINE_HASH_FROM_GET \
  --expected-policy-sha256 POLICY_HASH_FROM_GET
```

**由工作台创建和管理的工作，请在工作台保存设置。** CLI 的 `get` 仍可查看；`set/reset/restore` 会在任何写入之前明确拒绝，避免修改实例清单后工作台自己的配置摘要没有同步。工作台通过原有认证管理入口一起更新两份记录，没有放宽完整性校验。

没有 `per_layer_settings_v1` 的旧实例继续使用原有五层启用位和全局模式，不能写入新选项；界面也不显示不支持的控件。新增选项的默认值不会改变旧的持久绑定。带 `live_settings_v1` 的实例可以在运行中修改支持的设置；更旧的实例必须先确认停止。需要新选项时新建实例，不能直接改 feature 标记或被固定的代码文件。

设置改变会使未使用的审批与待确认草稿失效，不改变已积累的资料权限，不解除暂停或永久撤销，也不追溯取消已经开始的操作。审计写入失败和权限拒绝仍会停止执行，逐层观察不能绕过这些边界。

## 验证范围

逐层模式与扫描开关的首个检查点为六套件 **160/160**，其中运行中设置 **7/7**，浏览器设置 **12/12**。后续又加入审计、创建时设置恢复和所有工作台保存的版本核对；当前结果见[后续验证记录](evidence/settings-history-2026-09-12/REPORT.zh-CN.md)，不沿用首个检查点为新代码背书。Windows 的规则与扫描套件为 **37 通过、11 跳过**，跳过项要求 Linux 的安全文件读取。

这些是规则、真实本机 HTTP/Unix socket、持久状态与浏览器组件测试，检查模型回复为预设测试数据。没有运行真实模型、危险命令或原生 Agent 会话，不能用这些数字声称新版五层实机演示已通过。
