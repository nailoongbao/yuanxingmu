# 后台提醒

元星木可以在工作暂停、恢复、权限收回或等待本人确认时，向你设置的接收服务发送一条状态提醒。**可以关闭浏览器；启动工作台的进程必须保持运行。** 这项功能默认关闭，与需要保留网页的本机桌面通知相互独立。

在工作台展开“后台提醒”，填写接收地址和可选凭证，再保存。首次启用从当时读取到的工作记录末尾开始，不补发之前的历史告警。之后创建的新工作也会加入提醒。工作台停止期间不发送；使用原数据目录重新启动后，读取已保存位置之后的事件，并继续发送尚未完成的提醒。

目前接收服务需要支持下面的通用 JSON 协议。**尚未验收飞书、Slack、企业微信或邮箱等第三方通知服务**；不能把它宣传成直接支持这些提供商。提醒也不是手机系统推送服务。

## 提醒哪些事情

| 工作记录 | 提醒状态 |
|---|---|
| 防护触发整项工作暂停 | `paused` |
| 本人在主机核对当前事件后恢复 | `resumed` |
| 成功收回工作或子任务权限 | `revoked` |
| 工具操作需要人工审批 | `approval_required` |
| 新邮件草稿，或消息、上传、表单、覆盖、删除文件提案 | `approval_required` |

失败的恢复、失败的撤权、已被防护规则直接阻止的工具审批请求，不会被当作这些状态发送。扫描器只读取固定工作目录内经过身份校验的权限数据库，不接收 AI 提供的文件路径、接收地址或消息正文。不同事件使用不同编号，同一事件重扫时编号不变。

提醒正文只包含四个字段，例如：

```json
{
  "version": 1,
  "event_id": "不包含工作名称的稳定事件编号",
  "status": "paused",
  "message": "工作已暂停，请在元星木工作台查看。"
}
```

没有资料正文、候选指令、工作名称、草稿或模型输出。接收地址和凭证保存在工作台私有 `catalog.json` 内，不交给 Agent。浏览器不保存它们；提交、取消编辑、收起设置、页面关闭或访问失效时清空输入。状态接口只返回接收服务的域名和端口，不回显完整路径与凭证。

## 接收、重试与失败

主机向固定地址发送 `POST`，使用 `Content-Type: application/json`。可选凭证作为 `Authorization: Bearer …` 发送；稳定的 `Idempotency-Key: yuanxingmu-notification:<event_id>` 可供接收端去重。地址须为 HTTPS，只有明确的本机回环 IP 可以使用 HTTP；不允许账号、查询参数或页面锚点，也不跟随重定向。

默认任何 `2xx` 响应表示接收服务已确认，响应正文不保存。若开启逐条确认，接收服务必须返回 `{"accepted": true, "event_id": "原事件编号"}`，且不能出现多余或重复字段。**服务确认不代表本人已读。**

网络失败、超时、`408/425/429` 和 `5xx` 会有限次重试；重定向、其他 `4xx` 或无效的严格回执记为失败。默认每次最多等待 5 秒，最多尝试 5 次。总等待时限不会被缓慢读取响应延长。结果不明时仍可能重发，因此接收端应按稳定编号去重，不能宣称“恰好发送一次”。

重试等待使用 Linux 单调计时，调整系统日期不会让提醒卡住，也不会让另一进程提前接手尚未到期的发送。重新打开工作台会沿用本次系统启动内的等待期限；系统重启后仍保留事件编号和已经尝试的次数，待重试的提醒最多重新等待一个设定的退避周期，次数耗尽的不再发送。

**升级到这份实现前，先停止旧工作台，再用原数据目录启动新版。** 提醒数据库会在事务中从格式 1 迁移到格式 2，不能让新旧工作台同时使用同一队列，也不能直接用旧代码打开迁移后的队列。旧格式中无法确认所属系统启动的“发送中”记录，会额外等满一次发送时限加 5 秒，再恢复处理；不会清零尝试次数或生成新事件编号。

工作台显示等待、发送中、接收服务确认和发送失败。提醒记录满时，不会跳过对应工作事件的读取位置；已经发送的记录也计入容量，以保留持久去重证据。存储无法核实时显示数量未知，不会将它显示成零条失败。提醒失败、超时或服务确认都不会恢复暂停、批准操作或改变权限。

## 更换设置和关闭

更换接收地址、凭证或发送设置时，先停止旧发送队列，再启用新的记录。原始队列留在本机，不转发旧提醒给新目标。关闭后重新启用，同样从新的事件开始；工作台保留最近 20 次停止时的发送数量快照。完全相同的设置不会重建队列；同一个保存请求重复提交只返回原操作记录。

关闭或换目标会请求取消正在进行的网络操作，但已经发出的请求可能到达接收服务，无法承诺撤回。工作台关闭也会停止提醒服务，但不会因此终止仍在运行的 AI。需要停止 AI 时，请使用该工作的“暂时关闭”。

达到记录上限时，界面会明确告知。关闭后重新启用可以建立新记录，但旧记录中的提醒不再补发；它不是自动清理或无损迁移功能。

## 验证范围

- [持久队列测试](../tests/test_yuanxingmu_notifications.py)：Linux/WSL 当前 **28/28**。真实本机 HTTP 接收端；包括有限重试、稳定编号、严格回执、超时后迟到响应、并发、进程崩溃后的领取恢复、存储替换和取消，以及确定性的时间回拨/快进、跨实例重开、系统重启、耗尽次数保留和旧格式迁移。旧 23 项已包含在当前 28 项内，不相加。
- [工作台集成测试](../tests/test_yuanxingmu_alerts.py)：Linux/WSL **15/15**。真实工作台 HTTP、私有目录、权限数据库和接收端；包括重启补投、新工作、游标重放去重、切换目标、容量与故障。实际 Broker 的暂停、恢复和撤权在通知被拒绝时仍保持正确。运行环境使用测试安装文件，没有启动原生模型。
- [页面交互测试](../tests/test_yuanxingmu_alerts_ui.mjs)：Chrome **22 项通过**。生产 HTML、主脚本与提醒组件，API 响应为隔离的合成数据；核对清空凭证、未知结果只查询原请求、窄屏布局、失败/满额/数量未知的呈现。截图中的事件也是合成状态，不能充作真实通知送达证据。

这些证据验证本机后台链路，不代表任意第三方接收服务或每个原生 Agent 的全部通知场景已验收。
