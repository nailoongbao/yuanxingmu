# 一次设好范围，让 AI 自己完成

创建工作时，选择哪些固定对象可以接收这次工作的资料。之后，AI 发消息、上传文本或提交表单，只要在这个范围内、通过防护检查，就会直接执行。用户可以在工作台查看结果，不需要每一步再点批准。

这项能力先接入本仓库开发版的 Hermes 和 OpenClaw。现有安装器与早期演示使用旧版本；更新源码不会给已创建的工作追加自动执行权限。

## 怎样使用

1. 在工作台登记消息、上传或表单的接收对象。
2. 创建新工作，写明要完成什么。在“自动执行范围”中勾选允许接收本次资料的对象。
3. 开始聊天。AI 可用新的 `yuanxingmu_request_action` 完成授权内的操作；工作台保存执行记录和接收端回执。

网页默认最多尝试 8 次，每次请求正文最多 8 KiB，合计最多 64 KiB。上传包装、表单编码也计入大小。子任务共用这份额度，新建聊天或重启不会重新获得额度。这里的成功确认表示接收服务接受请求，不表示所有第三方后续处理已经完成。

没有勾选对象就不启用自动提交。界面不预选接收对象，因为授权内容是“这个对象可接收本次工作的资料”。AI 判断一段内容看起来公开，也不能自行去掉任务已有的资料限制。

## 什么情况还需要处理

| 情况 | 系统行为 |
| --- | --- |
| 固定对象、额度足够、资料权限允许，且防护检查通过 | 自动执行一次，保存实际结果。 |
| 新对象、额度不足，或改为删除、覆盖文件 | 保留待核对的提案；继续其他已授权工作。原生自动工具仅提供消息、上传和表单三类。 |
| 对方无权接收任务接触过的资料 | 拒绝自动发送。模型的“允许”不能覆盖资料权限。 |
| 请求已尝试，但结果不明确 | 保留未知结果；相同目标和正文即使换请求编号或子任务也不自动重发，不退回已消耗额度。 |
| 外部资料整段被输入规则扣留 | 该段不交给 AI，其他已授权工作继续，无需点“恢复工作”。 |
| 危险指令、记忆污染、偏离目标，或防护服务记录失败 | 继续拦截；有必要时暂停整项工作，保留原因。 |

原有 `yuanxingmu_prepare_action` 和邮件起草工具仍只生成待核对内容。系统不会把“帮我准备一下”悄悄变成执行；即使对同一个请求改调用自动工具，也不升级旧提案。

自动执行记录显示 `execution_mode=automatic`、授权来源 `frozen_task_scope` 和授权时间；`approved_at` 为空。人工确认才记录本人确认时间。二者均保存实际执行尝试和结果。

重复检查按规范化后的完整内容进行，不能识别任意改写措辞后的语义重复；变更后的操作仍受原目标、资料权限、防护检查和总额度限制。

## 输入隔离为什么可以不暂停

新建的受防护工作带有 `input_containment_v1`。只有输入规则确认整段内容已经扣留，且防护记录成功时，才继续其他工作。原始危险文本不会返回给 Agent。

这不会清除资料限制、放行待确认操作、解除先前暂停或恢复已撤销的权限。检查器出错、审计写入失败或其他层拦截，仍按原来的暂停方式处理。没有这个特性的旧工作保留原行为。

## 开发者接入

两个原生框架的创建函数都接收 `action_automation`。CLI 为 `openclaw init` 和 `hermes init` 增加 `--action-automation scope.json`，同时需要 `--action-targets targets.json` 和工作目标或防护配置。

```json
{
  "version": 1,
  "max_attempts": 8,
  "max_total_body_bytes": 65536,
  "targets": {
    "team": {
      "accepted_labels": ["private"],
      "max_body_bytes": 8192
    }
  }
}
```

`team` 必须是宿主登记的消息、上传或表单对象。上述配置表示该对象被明确授权接收本次私有工作资料。地址和凭证不来自 Agent 参数，配置被保存到宿主私有 `action-automation.json` 并绑定创建时摘要。

网页提交同时携带刚读取的对象摘要；服务端在接收请求和执行创建时核对。对象发生变化，旧勾选不能授权新地址。已创建的工作保留原对象快照。

执行前先检查实际规范化候选，再在同一数据库事务内检查当前资料权限并记入额度，之后才开始网络请求。候选重试、人工编辑过的旧提案、重启和最后一个额度的竞争均有独立回归测试。组件测试使用合成检查结果与本机真实接收端，不代表实际模型的判断准确率。原生 WebUI 验收另附录屏与记录。

检查模型还会收到宿主单独提供的授权事实：哪些固定对象已选中、当前子任务是否有权使用、资料权限是否相容、剩余额度，以及本任务最近八条操作结果。模型不需要根据回答中的“已获授权”猜测用户是否同意；它仍须检查正文有没有违反工作目标，例如禁止送出的内部底价。

这些事实来自宿主记录，不能由工具参数或外部资料提供。同名的 `host_facts` 出现在候选正文中仍只是待检查内容。事实不包含接收地址、凭据、操作正文或其他任务的记录，也不取代执行前的事务核验。检查失败仍可能阻止正常工作；提供事实不能保证模型不会误判。

对于真实 `request_action` 调用，宿主还会说明本次调用能否自动执行：已登记但未勾选的对象只能建立待核对记录，不会向对象发送任何内容。这样检查器可以区分“请求本人核对”和“立即执行”。这是实际派发分支提供的事实，伪造工具名称或在正文声称“只是草稿”不能取得它。正文里的禁发内容和工作目标明确禁止的对象仍要拦截；后续真正执行仍需本人确认或原有自动授权。
