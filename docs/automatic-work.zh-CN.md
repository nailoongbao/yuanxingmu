# 一次圈定可信边界，让 AI 放手闭环作业

先选好本次能接收资料的固定对象。范围内且通过检查的消息、上传和表单会执行一次，工作台保存实际结果。用户可以在工作台查看结果，不需要每一步再点批准。

这项自动化特性现已深度接入本仓库开发版的 Hermes 与 OpenClaw 原生框架中。已发布的历史安装器与早期演示视频基于老版本录制；需要说明的是：单纯更新代码源码并不会悄悄为历史已有任务追加自动执行特权。

## 极简三步上手指南

1. **登记受信对象**：在工作台面板中，提前录入允许接收消息、存储上传或表单写入的可信目标（例如在测试环境中登记特定的接收服务）。
2. **设立纪律并划定边界**：创建新任务，写明该任务的明确使命与约束。在“自动执行范围”选项中，勾选允许接收本次资料的目标。
3. **如常开始对话**：直接在会话中向 AI 下达任务。在授权范围内，AI 可自主调用全新升级的 `yuanxingmu_request_action` 工具顺畅完成交付；工作台会在底层同步落盘真实的执行流水与目标服务的物理回执。

在前端默认策略下，单个任务最多支持尝试 8 次自动化动作，单次提交载荷上限为 8 KiB，全任务累计交付上限为 64 KiB（上传封装与表单 URL 编码等开销均计入体积）。所有衍生子任务严格共享这份额度池，新起聊天或重启进程均不可重置额度。需要提醒的是：此处的“成功状态”仅代表目标接收端已按规范接收到 HTTP 请求，并不代表第三方后台的长链路业务已全部处理完毕。本机合成接收器的成功测试记录也不能等同于已经接通任意真实群聊平台。

**如果创建任务时未勾选任何目标，系统将完全不启用自动提交功能。** 出于严密的防御考量，系统界面绝不会为你“默认全选”任何接收方，因为每一次勾选本质上都是在签发“允许该实体接触本次私密数据”的安全承诺。即使大模型在推理过程中自我感觉“这段文本看上去挺公开、挺安全的”，它在底层也绝对没有权限私自撕毁任务已绑定的数据安全标签。

## 场景速查：哪些情况会自动放行？何时必须人工介入？

| 业务场景 | 系统的真实防御行为 |
| --- | --- |
| **固定对象、额度充裕、数据权限允许，且防护检查通过** | **自动执行一次**，保存实际结果。 |
| **出现未勾选的新目标、消耗超过额度上限，或试图删除/覆盖文件** | **保留待核对提案**：沙盒内其他已获授权的正常作业不受干扰继续推进。原生自动工具仅限消息、上传与表单三大类。 |
| **目标实体无权接收当前任务已沾染过的私密资料** | **坚决阻断自动发送**。即使大模型在 Prompt 里极力辩解“判定安全允许”，也绝不可凌驾于宿主权限账本之上。 |
| **网络抖动导致请求已发出但最终状态不明** | **保留未知结果**：相同的目标与正文，哪怕更换请求 ID 或换起子任务，也**绝不自动重试**，且不退回已消耗的额度。 |
| **外部资料整段被输入规则扣留** | **该段不交给 AI**，其他已授权工作继续，无需手动点击“恢复工作”。这项结论仅适用于被完整扣留的那段材料，并不代表能识别所有恶意输入。 |
| **检测到高危指令、记忆污染、任务意图偏离或防护服务记录失败** | **继续拦截**：必要时暂停整项工作（暂停的是任务及后续受控请求，不是保证已经运行的操作立即停下），如实留存现场原因供人工排查。 |

请放心：原先的 `yuanxingmu_prepare_action` 与邮件起草工具依然严格保持“只生成草稿、静候人工确认”的原生行为。系统绝不会把用户的“帮我准备一下”擅自篡改为直接执行；即便面对同一个请求后续改调自动工具，系统也绝不会偷梁换柱去自动激活旧的草稿提案。

在审计日志中，自动化执行记录会清晰标记 `execution_mode=automatic`、授权来源 `frozen_task_scope` 与自动化触发时间戳；而 `approved_at` 则保持为空。只有经过人类亲自确认的操作才会盖上人工审批印戳，两者均完整记录真实的执行尝试与物理回执。

防重检查按规范化后的完整内容进行，无法完全穷尽通过自然语言花样重写后的语义重复；但无论措辞如何变化，所有衍生请求依然在底层受到初始白名单、数据标签、各阶段防护检查与总额度池的限制。

## 输入隔离机制：为何外部资料扣留时可以不暂停工作？

所有新建的受保护任务均原生内置 `input_containment_v1` 隔离规范。只有当输入规则明确证实整段外部恶意内容已被完整扣留拦截、且安全审计记录成功时，沙盒才会放行其他合规的常规工作继续运转。原始的危险注入文本绝不会返回给 Agent。注意：这一结论仅适用于完整扣留的那段材料，不能扩大成识别所有恶意输入。

这项特性绝不会偷换概念去清除已有的数据安全标签、绝不擅自放行待审操作、绝不自动解除先前的安全挂起状态，更绝不可能擅自恢复已被撤销的权限。若检查器发生内部异常、审计写入失败或其他层拦截，系统依然会严格按照原有的暂停任务方式处理。未启用该特性的历史遗留任务继续保留原有行为。

## 开发者与高阶接入规范

两大原生 Agent 框架的工厂函数均原生支持接入 `action_automation`。CLI 命令行生态为 `openclaw init` 与 `hermes init` 扩展了 `--action-automation scope.json` 参数，同时需要配对提供 `--action-targets targets.json` 以及具体的工作目标或安全防护配置：

```json
{
  "version": 1,
  "max_attempts": 8,
  "max_total_body_bytes": 65536,
  "targets": {
    "team": {
      "accepted_labels": ["private"],
      "max_body_bytes": 8192
    }
  }
}
```

配置项中的 `team` 必须严格对应宿主机预先登记好的消息群组、上传网关或表单端点。上述范例声明了该端点已被人类管理员明确授权接收本次私密工作数据。真实的通信物理地址与凭证绝不由 Agent 参数传入，整套配置被保存到宿主私有权限下的明文 `action-automation.json` 中，并严格绑定创建时的特征摘要（附有创建时摘要，没有加密）。

在可视化网页端提交时，前端会同步携带刚读取到的目标对象数字摘要；宿主服务端在握手接收与执行建档的双重阶段均会做严格核对。一旦底层目标发生哪怕一丝变动，旧的授权勾选绝无法转移生效至新地址上。已建档的任务始终严格锁定创建那一刻的对象快照。

在任何网络请求真实离开发送前，系统会先对规范化后的载荷实施多层安全检查，随后在同一个不可分割的数据库事务（Transaction）内部比对当前数据污点标签并锁定额度，一切合规后方才启动底层网络通信。针对请求重试、人工二次编辑过的草稿、系统重启恢复以及临界额度的并发竞争，代码库均编写了完备的回归验证套件。单元测试基于合成的沙箱判定结果与本地真实接收端构建，并不代表商用大模型在真实场景下的绝对判断准确率；原生 WebUI 的全流程评测均附带真实的录屏与日志报告备查。

负责出站审查的安全模型，会额外接收到宿主以可信信道独立注入的“系统客观事实”：包括哪些固定对象已选中、当前子任务是否有权使用、资料权限是否相容、剩余额度，以及本任务最近 8 笔操作的历史执行结果。如此一来，审查模型完全无需根据上下文里大模型自言自语的“我已获授权”去猜谜；审查模型的核心使命唯有一条——严密审查正文文本是否夹带了违背工作初衷的内容（例如被明令禁止带出的内部核心商业底价）。

这些事实凭据来自宿主 SQLite 记录，绝不允许被工具入参或外部资料所篡改。即使攻击者在提示词中故意伪造同名的 `host_facts` 字段，在审查器眼里依然仅是一段待审的普通内容。客观事实凭据中绝不包含任何敏感的明文 API 密钥、接收地址、私密凭据、操作正文或其他任务的记录，也不取代执行前的事务核验。若审查模型发生超时或判定失败，仍可能阻止正常工作；提供事实凭据有助于减少误判，但无法保证模型不会误判。

对于真实的 `request_action` 工具调用，宿主还会向其明确传达本次调用能否自动执行：若调用的对象属于已登记但未被勾选的目标，系统在底层只会为其建立待核对记录，不会向对象发送任何内容。这样审查器可以清晰区分“请求本人核对”还是“立即执行”。这是实际派发分支提供的事实，伪造工具名称或在正文声称“只是草稿”不能取得它。正文里的禁发内容和工作目标明确禁止的对象仍要拦截；后续真正执行仍需本人确认或原有的自动授权。
