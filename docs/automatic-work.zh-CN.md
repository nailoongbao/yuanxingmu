# 一次圈定可信边界，让 AI 放手闭环作业

在创建任务时，你可以预先圈定好允许接收本次交付物的固定对象白名单。此后，AI 无论是在群聊下发进度消息、向指定存储上传文本文档，还是向系统提交结构化表单，只要严格落在这个受信范围内、且顺利通过各项安全审计，均可全自动流畅执行。所有执行流水与回执账本均实时留存在工作台中，你无需在每一步琐碎操作前反复手动点批准。

这项自动化特性现已深度接入本仓库开发版的 Hermes 与 OpenClaw 原生框架中。已发布的历史安装器与早期演示视频基于老版本录制；需要说明的是：单纯更新代码源码并不会悄悄为历史已有任务追加自动执行特权。

## 极简三步上手指南

1. **登记受信对象**：在工作台面板中，提前录入允许接收消息、存储上传或表单写入的可信目标（如指定内部项目群、归档服务器等）。
2. **设立纪律并划定边界**：创建新任务，写明该任务的明确使命与约束。在“自动执行范围”选项中，勾选允许接收本次资料的目标白名单。
3. **如常开始对话**：直接在会话中向 AI 下达任务。在授权范围内，AI 可自主调用全新升级的 `yuanxingmu_request_action` 工具顺畅完成交付；工作台会在底层同步落盘真实的执行流水与目标服务的物理回执。

在前端默认策略下，单个任务最多支持尝试 8 次自动化动作，单次提交载荷上限为 8 KiB，全任务累计交付上限为 64 KiB（上传封装与表单 URL 编码等开销均计入体积）。所有衍生子任务严格共享这份额度池，新起聊天或重启进程均不可重置额度。需要提醒的是：此处的“成功状态”仅代表目标接收端已按规范接收到 HTTP 请求，并不代表第三方后台的长链路业务已全部处理完毕。

**如果创建任务时未勾选任何目标，系统将完全不启用自动提交功能。** 出于严密的防御考量，系统界面绝不会为你“默认全选”任何接收方，因为每一次勾选本质上都是在签发“允许该实体接触本次私密数据”的安全承诺。即使大模型在推理过程中自我感觉“这段文本看上去挺公开、挺安全的”，它在底层也绝对没有权限私自撕毁任务已绑定的数据安全标签。

## 场景速查：哪些情况会自动放行？何时必须人工介入？

| 业务场景 | 系统的真实防御行为 |
| --- | --- |
| **目标在白名单内、额度充裕、数据权限兼容，且五层检查全部绿灯** | **直接全自动执行**，实时落盘真实的执行流水与回执记录。 |
| **出现未勾选的新目标、消耗超过额度上限，或试图删除/覆盖文件** | **自动降级拦截**：就地生成待审提案等待人工复核；沙盒内其他已获授权的正常作业不受干扰继续推进。原生自动工具仅限消息、上传与表单三大类。 |
| **目标实体无权接收当前任务已沾染过的私密资料** | **坚决阻断外发**。即使大模型在 Prompt 里极力辩解“判定安全允许”，也绝不可凌驾于操作系统与宿主账本之上。 |
| **网络抖动导致请求已发出但最终状态不明** | **审慎冻结未知状态**：相同的目标与正文载荷，哪怕更换请求 ID 或换起子任务，也**绝不自动重试**，且不回退已消耗的额度。 |
| **外部输入被安全规则判定为恶意注入并被就地扣留** | **无感隔离**：该段危险文本被宿主拦截，绝不喂给 AI，而沙盒内其他正常工作不受阻碍继续进行，你无需手动点击“恢复工作”。 |
| **检测到高危 Shell 指令、记忆污染、任务意图偏离或审计服务异常** | **立即停机挂起**：必要时当场冻结整项工作沙盒，如实留存现场原因供人工排查。 |

请放心：原先的 `yuanxingmu_prepare_action` 与邮件起草工具依然严格保持“只生成草稿、静候人工确认”的原生行为。系统绝不会把用户的“帮我准备一下”擅自篡改为直接执行；即便面对同一个请求后续改调自动工具，系统也绝不会偷梁换柱去自动激活旧的草稿提案。

在审计日志中，自动化执行记录会清晰标记 `execution_mode=automatic`、授权来源 `frozen_task_scope` 与自动化触发时间戳；而 `approved_at` 则保持为空。只有经过人类亲自确认的操作才会盖上人工审批印戳，两者均完整记录真实的执行尝试与物理回执。

防重机制基于规范化后的完整二进制载荷进行校验，无法完全穷尽通过自然语言花样重写后的语义重复；但无论措辞如何变化，所有衍生请求依然在底层受到初始白名单、数据标签、五层检查与总额度池的硬性封锁。

## 输入隔离机制：为何恶意输入被扣留时无需暂停整个工作？

所有新建的受保护任务均原生内置 `input_containment_v1` 隔离规范。只有当输入清洗规则明确证实整段外部恶意内容已被完整扣留拦截、且安全审计日志已持久化落盘成功后，沙盒才会放行其他合规的常规工作继续运转。原始的危险注入文本绝无可能被漏进上下文中送给 Agent。

这项特性绝不会偷换概念去清除已有的数据安全标签、绝不擅自放行待审操作、绝不自动解除先前的安全挂起状态，更绝不可能擅自恢复已被撤销的权限。若检查器发生内部异常、审计写入失败或触碰到了其他防御层的红线，系统依然会严格回退至整机挂起策略。未启用该特性的历史遗留任务继续保留原有行为。

## 开发者与高阶接入规范

两大原生 Agent 框架的工厂函数均原生支持接入 `action_automation`。CLI 命令行生态为 `openclaw init` 与 `hermes init` 扩展了 `--action-automation scope.json` 参数，同时需要配对提供 `--action-targets targets.json` 以及具体的工作目标或安全防护配置：

```json
{
  "version": 1,
  "max_attempts": 8,
  "max_total_body_bytes": 65536,
  "targets": {
    "team": {
      "accepted_labels": ["private"],
      "max_body_bytes": 8192
    }
  }
}
```

配置项中的 `team` 必须严格对应宿主机预先登记好的消息群组、上传网关或表单端点。上述范例声明了该端点已被人类管理员明确授权接收本次私密工作数据。真实的通信物理地址与鉴权密钥绝不由 Agent 参数传入，整套配置会被加密固化至宿主私有的 `action-automation.json` 中，并严格绑定创建时的特征哈希。

在可视化网页端提交时，前端会同步携带刚读取到的目标对象数字摘要；宿主服务端在握手接收与执行建档的双重阶段均会做严格哈希比对。一旦底层目标发生哪怕一丝变动，旧的授权勾选绝无法转移生效至新地址上。已建档的任务始终严格锁定创建那一刻的对象快照。

在任何网络请求真实离开发送前，系统会先对规范化后的载荷实施多层安全检查，随后在同一个不可分割的数据库事务（Transaction）内部比对当前数据污点标签并锁定额度，一切合规后方才启动底层网络 Socket 通信。针对请求重试、人工二次编辑过的草稿、系统重启恢复以及临界额度的并发竞争，代码库均编写了完备的回归验证套件。单元测试基于合成的沙箱判定结果与本地真实接收端构建，并不代表商用大模型在真实场景下的绝对判断准确率；原生 WebUI 的全流程评测均附带真实的录屏与日志报告备查。

负责出站审查的安全模型，会额外接收到宿主以可信信道独立注入的“系统客观事实”：包括哪些白名单对象已被勾选、当前子任务是否有权调用、数据标签是否匹配、额度水位结余，以及该任务最近 8 笔操作的历史执行结果。如此一来，审查模型完全无需根据上下文里大模型自言自语的“我已获授权”去猜谜；审查模型的核心使命唯有一条——严密审查正文文本是否夹带了违背工作初衷的内容（例如被明令禁止带出的内部核心商业底价）。

这些事实凭据完全源于宿主机内核的只读日志，绝不允许被工具入参或外部资料所篡改。即使攻击者在提示词中故意伪造同名的 `host_facts` 字段，在审查器眼里依然仅是一段待审的普通文本。客观事实凭据中绝不包含任何敏感的明文 API 密钥、私密通信令牌或跨任务数据，更绝不能取代实际执行前微秒级的系统事务核验。若审查模型发生超时或内部错误，系统宁可保守阻断正常工作也绝不放行；提供事实凭据有助于减少误判，但无法在理论上根除模型本身的判断失误。

对于真实的 `request_action` 工具调用，宿主还会向其明确传达本次调用是否具备自动执行资格：若调用的对象属于已登记但未被勾选的目标，系统在底层只会为其静默建档待审记录，绝不会向目标网络端点发出半个字节的载荷。借助这一机制，安全审查器能够清晰区分“这只是一份等待人类复核的提案”还是“即将真实射出的网络数据”。这一特权来自于底层派发引擎的硬性判定，任何在正文中声称“我这只是草稿”、或伪造工具名称的把戏都无法骗取直接执行权限。无论何时，只要正文违背了安全底线，系统依然会坚决予以拦截；后续若要真正生效，依然需要人类的亲手确认，或回到受信任的自动化授权框架中重新核验。
