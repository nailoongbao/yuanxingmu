# 为什么做元星木

2026-09-11。目标用户是给公司接入 Agent 的安全工程师。2–4 人团队应该做一套能实际控制执行的开源核心，再把它接进已有 Agent。仓库增长来自别人运行、复用和贡献的价值；当前没有万星或商业转化证据。

## 把哪件事做大

公司应该能说清楚：“这个任务允许读取哪些资料，把结果交给谁，哪些动作必须撤销。”即使模型被网页、邮件或工具返回操控，它仍不能自行扩大这些权限。

最终产品应把任务权限、私密资料、对外动作和可核查的执行记录连在一起。安全工程师可以给 OpenClaw、Hermes 等已有 Agent 配置一次边界，在模型和工具升级后继续复测；发现越权时撤销任务，并看到它及其子任务实际停止了哪些动作。

当前已做出来的是第一段：持久权限库、固定资源/目的地的执行服务、Linux 隔离和真实接收端验收。原生框架接入、企业权限来源和多实例管理是后续产品工作。不能把第一段称作整个企业 Agent 已被保护。

## 为什么与模型能力增长相关

模型更强，可能减少无意工具错误，也可能更善于组合动作、尝试替代出口和隐藏意图。两者同时成立。把权限核对放在模型之外，可以让授权决定不依赖模型愿意遵守规则，但仍须持续检查是否漏了执行通道。

“内容安全完全与能力无关”也过于绝对：自动化传播、个性化操控和规模化欺诈会随能力变化。这里选择任务执行权限，是因为后果、权限和拦截位置更容易明确验证，而不是因为其他安全问题都没有价值。

真正需要研究的是：攻击者模型能力和尝试预算增加时，在同样正常业务要求下，仍能找到多少越权路径；防御为保住边界又牺牲了多少正常完成率。固定脚本演示只证明已测机制，不证明抵抗更强模型的能力曲线。

## 与 AgentWard / 玄甲的对照

核查对象为 [FIND-Lab/AgentWard](https://github.com/FIND-Lab/AgentWard/tree/46309333bdfdbcf4701000c1dad85b33b4a0e7ef)，包版本 2026.5.9。以下区分源码能力和本地执行证据，没有关闭对方保护来制造胜负。

| 问题 | AgentWard 此提交 | 元星木当前状态 |
| --- | --- | --- |
| 是不是实际防御 | 是。OpenClaw 输入、记忆、执行钩子，规则和模型裁判，阻断与审批分支均有实现。 | 是。实际发送在 broker 中核对，Linux 网络/文件访问由 bubblewrap 约束。 |
| 日常产品完整度 | 有原生插件、配置命令、警告、审批卡与日志。 | 目前是 CLI 和开发接入原型，没有相同的审批管理界面。 |
| 权限由谁保管 | 插件检查 OpenClaw 提供的上下文与工具请求；宿主本身可另有沙箱。 | 任务状态与读取记录留在 worker 环境外，工作程序拿不到授权数据库。 |
| 恢复和子任务的读取限制 | 源码未发现与本原型等价的独立任务家族读取标签账本；不代表所有实际部署都没有外部控制。 | 合成真实进程已验证重连、broker 重启、已有子任务与撤销；框架原生恢复需单独实测。 |
| 谁防御更强 | 未完成双方正常安装、模型裁判就绪、同任务同预算的完整对照。 | 不能由一次原型实验证明整体超过它。 |

源码入口：[插件钩子](https://github.com/FIND-Lab/AgentWard/blob/46309333bdfdbcf4701000c1dad85b33b4a0e7ef/index.ts)、[配置](https://github.com/FIND-Lab/AgentWard/blob/46309333bdfdbcf4701000c1dad85b33b4a0e7ef/config.ts)、[会话状态](https://github.com/FIND-Lab/AgentWard/blob/46309333bdfdbcf4701000c1dad85b33b4a0e7ef/core/state.ts)。只检测一条命令正则是否命中，不能代表它包含模型裁判的完整防御。

要赢，必须在一个清楚的任务上做到对方尚未证明的完整结果，并保住正常工作。不能用更多框架 logo、更多测试数量或更漂亮的图冒充这种差异。

## 已有工作与新价值

[CaMeL](https://github.com/google-research/camel-prompt-injection) 已研究信息来源与允许读者；[Microsoft Agent Framework / FIDES](https://learn.microsoft.com/en-us/agent-framework/agents/security) 已实现会话标签和执行前检查；[bubblewrap](https://github.com/containers/bubblewrap) 提供实际 Linux 隔离。元星木不能把这些原理重新起名就当成发明。

[Hermes iron-proxy 文档](https://github.com/NousResearch/hermes-agent/blob/2237be355906fbe6065ce1815711eee52b2d646e/website/docs/user-guide/egress/iron-proxy.md)已经说明凭证代理的边界：直接 socket 绕过以及向允许域名夹带私密正文，不是仅靠代理替换密钥就能解决。元星木当前用关闭直接出口和任务读取限制处理限定工作环境中的这两个问题，仍需把所有宿主出口纳入同一权限归属。

值得积累的东西是可用接入、跨恢复和子任务的一致性、企业权限映射、失败关闭和正常业务兼容。它们也最难靠漂亮 demo 替代。

## 对开源与商业化的决定

开源应给出可运行的执行核心、OpenClaw/Hermes 接法、完整的失败记录和升级复测。第一次使用就能看到：不该发送的收不到，应该发送的能完成，且模型换了仍能用同一套验收。

商业部分可以围绕公司现有权限接入、集中配置和撤销、多实例审计、受控审批与运行支持收费。核心拦截不能故意做成不可用的展示版。现在没有付费客户或独立持续使用数据，商业化是方向判断。

对 2–4 人团队，接下来的顺序是：先完成两个宿主的一条业务链；再接一种真实的文档读取和外部提交服务；随后测试真实攻击模型在增加能力与预算时的表现。最后才扩更多框架。每一步都同时记录合法业务完成情况，不能通过禁止一切动作获得“安全”。
